## Findings

- **AS_DEVICE packet encoding is unchanged.** Complete class text for ASDeviceData (`peer-Commons.il:44622`), ASDeviceStateData (`:51048`), ASDeviceExtraData (`:50817`) is identical after build-directory normalization. MAC-last-byte/XOR identity, state masks HFP0x80/HFP-active0x40/A2DP0x20/in-ear0x04/SPP-connectable0x02 and extra sequence/volume fields retain previous meaning. This is normalized textual IL equivalence, not raw binary identity or a formal runtime-equivalence proof.
- **BaseContext remains wire-compatible for Auto Switch, with clearer property names and low-battery support.** Class `:45122`: AutoSwitchSettings int becomes IsAutoSwitchingEnabled bool, still `(feature & 0x02) != 0`; continuity0x01 and BTConnectionType0x04 retain positions. Feature now stores entire byte instead of split feature/RFU nibbles, and bit0x40 becomes IsLowBattery. Parsing preserves optional five-byte legacy account-ID behavior; generation writes feature byte. Whether the new PC sender sets Auto Switch is a separate main-executable question, unlike the old sender which left it clear.
- **No new registry admission limit/eviction found.** DiscoveredDeviceManager.AddDevice (`:86888`) is unchanged after build-directory normalization, as are remove methods. GetAllDiscoveredDevices (`:87754`) now additionally filters out CloudDeviceType0 before member-type mask filtering. This is a listing filter, not a radio connection cap or peer eviction policy. Whole-IL bounded searches for max-device/peer/connection and eviction found no explicit limit; firmware and main-executable policies remain outside this negative claim.
- **BLE envelope constants preserve company/service/PC identity and add sequencing metadata.** BleConst (`:91097`) retains Samsung0x75, service0x18, PC5, ONE_TO_N_SUPPORT_VERSION3; adds support-binary-sequence bit0x01, binary-sequence bit0x02, extended account info end13, background timeout25000ms and RSSI thresholds-100/-120/-127. These flags may improve discovery synchronization; constants alone prove no specific coexistence behavior. Version3 is not a three-host limit.
- **New cloud Buds inventory and IPC support are substantial.** BudsDeviceData (`:23810`) includes RecordId, DeviceName, MacAddress, IsPaired, DeviceType, ManufacturerData, ExtraValue. SCBluetoothEventsResponse (`:18338`) has updated/deleted records, checkpoint and pagination; SCBluetoothDocumentsResponse (`:18699`) has documents and next-page token. BudsSyncPipeResponse (`:64947`) returns StatusCode and a list of BudsDeviceData. BudsSyncStatusCode (`:64935`) enumerates success0, failed1, not-signed-in2, no-internet3, unauthenticated-for-SC4, skipped5. PipeMessageID adds BudsSync301 and BudsGetAllDeviceInfo302 (`:65400`); protocol host budsquery appears `:67001`. These are concrete new contracts, but actual cloud reads/writes, authorization and effect on Buds topology require caller tracing; neither ExtraValue nor IsPaired proves key-sharing.
- **Buds Auto Switch is enabled by feature gate on all PCs in this module.** New CommonUtils.FeatureConst.get_IsBudsASSupported returns true unconditionally (`:92189`); adjacent FamilyMDE/P2P gates still consult Samsung-device identity. This is module policy, not proof all hardware succeeds.
- **Generic AUTOSWITCHING event handling remains unchanged.** HandlerFactory class text matches old after build-directory normalization; ID1 remains wrapped in generic BaseHandler, not a newly specialized policy here.

## Scope and next evidence

Unresolved: exact account participation/identity sent to Buds, per-host connection priority, firmware's active link capacity, four-host behavior, and the cause of Linux evicting native peers.
