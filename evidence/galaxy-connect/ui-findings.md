## Observations

- UI-01: Full GalaxyConnectWinUI.il (239,744 lines) has no case-insensitive matches for `buds`, `easyconnect`, `autoswitch`, or `auto.switch`. Its referenced assemblies include GCEAppCommon, CommonsNet, SettingsSDK and SASDK_WinUI, with no EasyConnect2/ExtensionCommon reference. This is a bounded negative in this assembly, not evidence that the full continuity package cannot affect Buds.
- UI-02: GalaxyConnectedExperience.Services.ContinuitySettingsService uses `ModuleContinueApps` through SettingsSDK.ModuleFactory.Get, and falls back to `SOFTWARE\Samsung\SamsungSettings\ModuleContinueApps`, value `OnOff`. See GalaxyConnectWinUI.il 177369–177610 (IsSettingsSDKSupported, GetContinuitySettingsValue); the UI Settings bridge here controls continuity, not the Buds ModuleAutoSwitch.
- UI-03: The actual Buds Settings UI is SamsungSettings.ViewModel.AutoSwitchBudsVM in the already decoded evidence/SamsungSettings.il. get_ModuleName returns `ModuleAutoSwitch` at 159418. Constructor 159425–159471 obtains ExtensionCommon.Services.BudsInfoServiceFactory.Get and subscribes OnBudsListChanged. OnClick navigates AutoSwitchBudsDetail at 159497–159507. SetConfig at 159510–159524 calls SettingsSDK.ModuleFactory.Get("ModuleAutoSwitch").SetData(key,bool.ToIntString()). OnActiveDetail starts BudsInfoService change monitoring and reads GetList at 159538–159547. This establishes a Settings SDK module boundary rather than a direct UI call to EasyConnect2.
- UI-04: AutoSwitchBudsVM constructor resource keys at SamsungSettings.il 159436–159454 explicitly describe same Samsung account, prior connection to this PC, and not switching while another device plays media. These are displayed policy statements, not proof of enforcement or current Buds4 Pro firmware behavior.
- UI-05: Galaxy Connect has real Samsung account code, separately from its Buds-free UI. SAManagerService.GetSignInRequest constructs `samsung-mcfgalaxyconnect://sso` / `samsung-mcffamilymde://sso` callbacks at GalaxyConnectWinUI.il 207334–207404. SignInAsync uses SASDK SignInRequest/SetClientID/SetCodeVerifier/SetScope/SetState then SamsungAccountManager.SignIn at 205800–205821. After successful response parsing, the callback builds a SamsungAccountQueryInfo with SAStatus numeric 1, host type numeric 10, then MCFProtocolHelper.SendMessageToMCF at 203220–203243.
- UI-06: SyncWithSamsungAccount checks IsSignedInAsync then conditionally calls SyncSignInStatusAsync (206494–206552). SyncSignInStatusAsync obtains an access token, checks empty, and calls GetUserProfileDataAsync (206074–206120); GetUserProfileDataAsync passes the token/user id to the Samsung account SDK (204140–204157). These are code-level data flows, not recovered user tokens.
- UI-07: Bounded searches of this UI IL for `max.{0,12}device`, `device.{0,12}limit`, `MaxDevice`, `MAX_DEVICE`, `MaxCount` found no concrete Buds host-count limit. Generic Win32 enum error names are unrelated.

## Inferences and unknowns

The Galaxy Connect UI is a continuity/account frontend; the known Buds settings frontend uses ModuleAutoSwitch. A UI-only Galaxy Connect identity patch is unlikely to add four-host Buds coexistence because this assembly supplies no Buds packet path. Native MCF and EasyConnect2/ExtensionCommon module implementation remain the relevant places to establish actual coordinated discovery/account-group behavior. This pass does not establish four-host capacity, which protocol field would preserve other hosts, or whether account membership is the immediate cause of the observed disconnections.

No worker/settings/identity changes were made. No binary was executed. Runtime and firmware behavior remain unverified.
